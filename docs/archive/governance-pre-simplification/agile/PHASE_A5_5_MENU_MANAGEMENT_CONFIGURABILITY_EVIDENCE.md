## Persistence model

Flyway V16 adds `store_combo_groups` as the Store-level Combo group source:

- `store_id`
- `group_code`
- `name_zh`
- `name_en`
- `selection_rule`: `EXACTLY_ONE` or `OPTIONAL_ONE`
- `required`
- `enabled`
- `display_order`
- `default_component_code`
- `archived_at`

Flyway V16 extends `store_combo_components` without replacing it:

- `group_id`
- `linked_menu_item_id`
- `business_behavior`: `NO_KITCHEN_TASK`, `LINKED_MENU_ITEM`, or
  `LEGACY_COMBO_SIDE_TASK`
- `archived_at`

Legacy `COMBO_EGG` and `COMBO_SIDE` rows are deterministically mapped into
`store_combo_groups`. Existing St-Denis combo components remain:

- `combo_tea_egg`
- `combo_fried_egg`
- `combo_edamame`
- `combo_shredded_potato`
- `combo_cucumber_salad`

The V16 migration relaxes the old V12 hardcoded group/code CHECK constraints so
future Stores can have their own Store-scoped combo groups/components. It does
not drop the canonical `store_combo_components` table, rewrite historical
orders, edit Flyway history, create runtime Store data, or mutate Production.

Categories reuse the existing `menu_categories` model. Stations reuse the
existing `stations` model; V16 adds bilingual station names, controlled
`station_type`, and `archived_at`.

## Combo contract

Combo pricing remains unchanged:

- Combo price source: `store_pricing_policies.combo_delta`
- Item Combo allowed source: item-scoped `menu_item_options` `COMBO` row
- Store Combo group/component source: `store_combo_groups` and
  `store_combo_components`

Owner-created group and component codes are system-generated. Owners configure
names, enablement, display order, selection rule, default component, and optional
business mapping; they do not type database IDs, station IDs, or internal codes.

Delete in the UI maps to safe archive/deactivate semantics for existing combo
groups/components. Historical submitted orders, completed orders, receipts,
print snapshots, and reports remain snapshot-backed and are not reselected or
repriced.

Required enabled groups must have at least one enabled component and a valid
default. If a default is disabled or removed, the service selects the next
enabled component by display order or rejects the invalid required group.

## Business behavior contract

`business_behavior` is deliberately explicit:

- `NO_KITCHEN_TASK`: selectable combo component only; no independent kitchen
  task is generated.
- `LINKED_MENU_ITEM`: records a validated same-Store active menu item mapping
  for stable business identity and future routing/profile materialization.
- `LEGACY_COMBO_SIDE_TASK`: reserved for the three reviewed St-Denis side
  components whose historical order path already creates synthetic side tasks.

This package does not introduce hidden Store-specific code such as
`if St-Denis` or `if Chinatown`, and it does not pretend that every future
component automatically has kitchen routing. New routed behaviors require an
explicit component behavior contract rather than silent inference.

## Category contract

Menu Management now exposes Category create/update/delete controls backed by
Store-scoped APIs. Category codes are generated by the system and remain stable.

Safety:

- Deactivating a category with active menu items fails with
  `CATEGORY_HAS_ACTIVE_ITEMS`.
- Deleting a category with any menu item reference fails with
  `CATEGORY_NOT_EMPTY`.
- No silent cascade delete of menu items is allowed.

Each accepted category mutation locks the Store and increments
`stores.menu_revision` / `stores.menu_updated_at` in the same transaction.

## Station contract

Menu Management now exposes Station create/update/delete controls backed by
Store-scoped APIs. Station codes are generated by the system. Station type is a
controlled value:

```text
KITCHEN | BAR | COLD | PASS | OTHER
```

Safety:

- Deactivating a station with active menu items fails with
  `STATION_HAS_ACTIVE_ITEMS`.
- Deleting a station with any menu item reference fails with `STATION_IN_USE`.
- Disabling the legacy `COLD` station while enabled legacy combo side routing is
  present fails with `STATION_HAS_LEGACY_COMBO_SIDE_ROUTING`.

Each accepted station mutation locks the Store and increments
`stores.menu_revision` / `stores.menu_updated_at` in the same transaction.

## Frontend behavior

Menu Management presents the Owner-facing sections:

```text
Menu Items
Categories
Stations
Combo Configuration
Pricing Rules
```

The Combo Configuration panel supports `+ New Group`, `+ Add Item`, bilingual
names, enable/disable, display order, required/default selection, optional
linked menu item selection, and safe delete/archive. The ordering catalog maps
dynamic combo groups into `combo.groups` while preserving legacy Egg/Side
transport IDs for rollback-compatible snapshots.

IndexedDB keeps the existing complete-snapshot atomic switch model. Combo,
category, and station mutations advance the Store menu revision so Pad/Web
clients refresh as a whole revision rather than mixing partial menu graphs.

Repair root cause:

- `MENU_CACHE_HASH_MISMATCH`: the backend content hash included the A5.5
  `combo_configuration` group/component metadata (`group_id`, `group_code`,
  `selection_rule`, `required`, `enabled`, `display_order`, component ids,
  linked menu item metadata, and `business_behavior`), but the frontend
  IndexedDB validator omitted those same fields. After Combo Configuration
  changed, the Pad/Web candidate snapshot was correctly rejected instead of
  atomically replacing the active snapshot.
- Dynamic Drink group visibility and disabled Side/default behavior were
  downstream of the stale snapshot plus repeated legacy Egg/Side fallback
  selection logic. The repair keeps legacy Egg/Side transport compatibility but
  resolves every current combo group selection only against the new snapshot's
  enabled options, falling back to the current Store-configured default/first
  enabled option for new selections. Existing local draft line snapshots remain
  frozen and are not silently rewritten.
- Combo Configuration no longer exposes unlabeled raw `10` / `20` values as
  ordinary Owner configuration. The field remains `display_order`, is labeled
  `Display Order / 排序`, and the UI provides Up/Down controls while preserving
  stable group/component identity.

Repair validation added:

  catalog to `fnv1a32:07ab0e4f`.
- frontend hash tests cover dynamic group metadata, component metadata,
  default changes, disabled components, deterministic repeated reads, and
  legacy v2 validation.
- ordering tests cover dynamic Drink group mapping, disabled Coke removal,

remaining UI blocker in Combo Configuration: `Display Order / 排序`, Up/Down,

and component rows at common desktop/tablet widths.


business logic, defaults, enabled/disabled semantics, menu revision, pricing,
ordering, backend validation, Flyway/schema, Store Profile, or A6 module
gating.

Repository repair:

- `ComboConfigurationPanel` now uses explicit responsive CSS Grid layout
  contracts for group and component rows.
- `Display Order / 排序` keeps a dedicated minimum-width field.
- Up/Down controls move into their own `Reorder` grid column/container instead
  of sharing the Display Order input area.

  retain their own grid area at wide widths and wrap into readable two-column
  rows below the wide breakpoint.
- Up/Down labels remain visible/clickable, disabled state remains visible, and

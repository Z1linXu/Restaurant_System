## Owner product decision recorded

A0's underlying implementation direction remains accepted:

```text
OPTION + MODIFIER_GROUP + PRICE_DELTA
```

However, the Owner rejected the A0 Owner-facing Size UX because Size is not a
free-form option for this product. A0.1 tightens the product contract to these
system-controlled canonical Sizes only:

| Semantic Size | Chinese label | English label | Code |
|---|---|---|---|
| `SMALL` | `小碗` | `Small` | `size_small` |
| `REGULAR` | `中碗` | `Regular` | `size_regular` |
| `LARGE` | `大碗` | `Large` | `size_large` |

Owner/Admin must not create arbitrary Size labels/codes such as `Big`,
`Extra Large`, `大份`, or `标准份`. Future Size expansion requires a new
product/module contract.

The Owner also selected Store-level pricing as the canonical future source:

```text
item.base_price
+ Store Size delta
+ Store Combo delta when selected
+ other option deltas
```

Default initial Store policy:

| Policy key | Initial delta |
|---|---:|
| `SMALL_DELTA` | `-2.00` |
| `REGULAR_DELTA` | `0.00` |
| `LARGE_DELTA` | `2.00` |
| `COMBO_DELTA` | `5.00` |

## Current implementation audit

Current schema and code provide no Store-level pricing policy persistence.

| Domain | Current authority | A0.1 impact |
|---|---|---|
| Size identity | `menu_item_options` with `option_group=SIZE`, `option_type=size`, `option_code`, labels, `sort_order`, `is_active` | Reusable for per-item enabled Size configuration. |
| Size price | `menu_item_options.price_delta` per item option row | Not acceptable as the long-term canonical source for Store-level Size pricing. |
| Combo allowed | active item-level `menu_item_options` row with `option_group=COMBO` or legacy combo option | Reusable as per-item `COMBO_ALLOWED`. |
| Combo price | item-level combo option `price_delta`; frontend maps this as `combo.upcharge` | Not acceptable as the long-term canonical source for Store-level Combo pricing. |
| Store config | `stores` has identity/status/menu revision/printing fields; no pricing fields or generic settings table | A new additive schema is required. |
| Ordering price | frontend draft computes from catalog `base_price + option deltas`; backend saves submitted `unit_price_snapshot` and option `price_delta` snapshots | Good historical snapshot boundary; must be preserved. |
| Menu revision/cache | `stores.menu_revision`, `menu_updated_at`, `/api/v1/menu/catalog/revision`, IndexedDB complete snapshots and content hash | Pricing policy updates must increment menu revision and be part of the catalog/hash contract. |
| Printing | GRAB/HOT_KITCHEN use order/kitchen snapshots; Frontdesk receipt uses `order.subtotal_amount`, `order.total_amount`, `order_items.line_amount`, and `order_item_options.price_delta` | Good snapshot boundary; renderers must not read current pricing policy at print time. |
| Reporting | analytics aggregation uses order totals and `order_items.line_amount` | Good historical reporting boundary; policy changes must not reprice past sales. |

Because the current schema lacks a safe Store-level pricing policy table, A0.1
cannot be implemented without a new Flyway migration. Implementing policy in
frontend constants, raw runtime config, hidden `menu_item_options` rows, or
duplicated item-level deltas would preserve the exact product problem the Owner
rejected.

## Required schema design

Minimal additive schema:

```sql
CREATE TABLE public.store_pricing_policies (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    store_id bigint NOT NULL,
    size_small_delta numeric(38,2) NOT NULL,
    size_regular_delta numeric(38,2) NOT NULL,
    size_large_delta numeric(38,2) NOT NULL,
    combo_delta numeric(38,2) NOT NULL,
    policy_revision bigint NOT NULL DEFAULT 1,
    created_at timestamp(6) without time zone NOT NULL,
    updated_at timestamp(6) without time zone NOT NULL,
    CONSTRAINT uq_store_pricing_policies_store UNIQUE (store_id),
    CONSTRAINT fk_store_pricing_policies_store
        FOREIGN KEY (store_id) REFERENCES public.stores(id)
);

CREATE INDEX idx_store_pricing_policies_store
    ON public.store_pricing_policies (store_id);
```

The table is Store-scoped, additive, and independent per Store. It supports the
future Store Profile rule: profile values are defaults/snapshots that
materialize into each Store's own pricing policy and do not live-link back to
the source profile.

## Canonical source rules after approval

If the schema is approved:

1. `store_pricing_policies` becomes the canonical Size/Combo delta source.
2. `menu_item_options` remains the canonical per-item identity/enablement
   source for Size, Combo, add-ons, removes, noodle type, soup base, etc.
3. Size labels/codes are system-controlled:
   - `size_small` -> `小碗 / Small`
   - `size_regular` -> `中碗 / Regular`
   - `size_large` -> `大碗 / Large`
4. Owner Size UI becomes a controlled checkbox/select panel:
   - Small / Regular / Large enabled per item;
   - no free-form Size label/code input;
   - legacy inactive/noncanonical Size rows hidden from normal Owner UX.
5. Combo UI becomes per-item `COMBO_ALLOWED = true/false`.
6. Catalog responses expose effective Size/Combo price deltas from
   `store_pricing_policies`.
7. `menu_item_options.price_delta` for Size/Combo may be kept as a derived
   compatibility mirror for rollback/old-app safety, but it is not the source
   of truth once the policy is active.

## Default Size rule

The post-approval implementation should use this deterministic rule:

1. If `REGULAR` is enabled, `REGULAR` is the default and appears first in the
   catalog ordering.
2. If only one Size is enabled, that Size is auto-selected.
3. If multiple Sizes are enabled and `REGULAR` is not enabled, the request must
   include an explicit default Size code; the Owner UI should reveal this only
   for that uncommon case. No silent Small/Large guessing is allowed.

The actual known cases remain simple:

| Case | Default result |
|---|---|
| Small + Regular + Large | Regular |
| Regular + Large | Regular |
| Small + Regular | Regular |
| Regular only | Regular, auto-selected |

## Migration and backfill plan

The approved migration should be additive and Staging-first:

1. Create `store_pricing_policies`.
2. Backfill one row per existing Store.
3. For each Store, derive candidate deltas from active canonical
   `menu_item_options` rows where possible:
   - `option_group=SIZE`, `option_type=size`, `option_code IN
     ('size_small','size_regular','size_large')`;
   - active combo row with canonical/legacy combo semantic for `combo_delta`.
4. If all active rows for a Store and semantic code agree, use that value.
5. If a Store lacks rows for a semantic, use the product default.
6. If active rows for the same Store and semantic have conflicting deltas,
   fail closed before enabling the new application behavior and stop at:

```text
PHASE_A0_1_PRICING_POLICY_BACKFILL_CONFLICT_WAITING_FOR_OWNER_DECISION
```

Do not guess conflicting Production runtime price policy.

## Backward and forward compatibility

- Historical submitted/completed orders remain unchanged because order pricing
  is already frozen in `orders`, `order_items`, and `order_item_options`.
- Existing draft lines retain their local/order-line price snapshot.
- New lines after a policy revision use the newly downloaded catalog snapshot.
- Printing renderers keep using order snapshots; no print-time repricing.
- Reporting keeps using order totals and line snapshots; no historical sales
  rewrite.
- Menu policy updates must increment `stores.menu_revision`, update
  `menu_updated_at`, and be included in catalog hash/etag semantics.
- IndexedDB menu cache must atomically replace the complete catalog snapshot;
  mixed old menu + new pricing policy is forbidden.
- Application rollback to a pre-A0.1 app remains possible because the new table
  is additive and ignored by old code. If approved implementation writes a
  compatibility mirror into Size/Combo `menu_item_options.price_delta`, old code
  will see the latest policy-equivalent deltas after rollback.

## Proposed API and UI contract after approval

New Owner/Admin API surface:

```text
GET  /api/v1/admin/menu/pricing-policy?store_id={storeId}
POST /api/v1/admin/menu/pricing-policy/preview
PUT  /api/v1/admin/menu/pricing-policy
PUT  /api/v1/admin/menu/items/{itemId}/size-configuration
PUT  /api/v1/admin/menu/items/{itemId}/combo-policy
```

Required UI:

- Menu Management item panel: `Size Configuration / 规格`
  checkboxes for Small/Regular/Large with system labels and no free-form Size
  code/name fields.
- Menu Management or Owner Admin entry: `Pricing Rules / 价格规则`.
- Pricing Rules shows Store-level Size deltas and Combo delta.
- Save opens an impact preview before confirmation.
- Impact Preview is computed from actual Store menu/config:
  - affected enabled Size items;
  - old/new effective prices;
  - disabled Size excluded;
  - combo-disabled item excluded;
  - cancel and confirm actions.
